2 · Four stores

Meet the four stores we'll compare

Redis

In-memory key → value
session:42→{cart…}user:7→{…}hits:home→1,204
Great sub-ms reads · key expiry (TTL) · counters
Weak RAM is expensive · no ad-hoc queries
Sessions · caches · rate limits · leaderboards

Postgres

Row-oriented relational (OLTP)
Great ACID transactions · indexes · fast updates
Weak scanning wide tables for analytics
System of record · app backends · orders · profiles

DuckDB / OLAP

Columnar analytical engine
Great scans · aggregations · compression · SQL on files
Weak single-row updates · many small writes
Analytics · BI · warehouses · embedded / laptop

S3 + Parquet

Object storage + open file format
📁 raw/📁 orders/▤ part-0.parquet▤ part-1.parquet
Great cheapest durable bytes · infinite scale · decoupled compute
Weak high first-byte latency · immutable files
Data lake · landing zone · archives · history

Same data can live in all four, each answers a different question well.

4:00 (3 min). One card at a time, 40 seconds each. For each: what shape is the data inside, what is it great at, what breaks it. Redis = a giant in-memory dictionary. Postgres = rows kept together so one record is one read. DuckDB = columns kept together so one column is one read. S3 = a bucket of immutable files; Parquet is the columnar file format inside. Tease: the demo uses all four on the same 5M orders.
3 · Which store?

Every store trades speed against cost

Order-of-magnitude, storage-only list prices (us-east-1 style). Log scale: RAM costs hundreds of times more per byte than object storage.

7:00 (1.5 min). All four rows show together and the bars grow on entry. There is no best store, only a best store per access pattern. Fast and cheap do not coexist, so architecture = putting each dataset on the cheapest tier that still meets its latency need.

4 · Deep dive · Session 2 · File formats & storage strategy

Same table. Two ways to lay it on disk.

The logical table

Each coloured block below is one value. Highlighted = the bytes a query must read.

A · get order #5 (one whole row)

B · SUM(amount) (one column, every row)

Row store wins when you want a whole record · column store wins when you want a few columns of many records, and each column compresses far better (same type, repeated values).

15:30 (2 min). Left: the logical table. Right, A: the row store reads one contiguous block (1 seek); the column store has to gather one value from each of 5 columns (5 seeks). B: the row store drags all 40 values through memory to reach 8; the column store reads one contiguous column. Compression: a column holds one type, so dictionary / delta / run-length encoding shrinks it 3-10x. Real numbers come in the demo: 1.29 GB in Postgres vs 116 MB as Parquet.

4 · Deep dive · skipping data (predicate pushdown)

One filter skips 40 of 41 row groups. Another skips none.

WHERE order_id = 4,200,000

Footer says only one row group's range contains it → 1 of 41 read. Measured locally ≈ 6 ms.

WHERE customer_id = 4242

Every row group's range spans 1 – 200,000 → 41 of 41 read. Measured locally ≈ 12 ms.

Sort or cluster data by the column you filter on most. Locally the gap is only ~2× because fixed HTTP overhead dominates; on real S3 every skipped row group is a skipped network request, so the gap grows with latency and data size. (Same idea as clustering keys in Snowflake / BigQuery, Session 3.)

18:30 (1 min). Green = read, grey = skipped. The engine reads the footer first, compares the filter to each chunk's min/max, and only fetches survivors. Be honest about the 2x: it is the mechanism that matters. Live version of both queries is in the demo.
4 · Deep dive · partitioning & formats

Partition by what you filter, not by what you have

s3://lake/orders_by_month/ ├─ order_year=2024/ (12 folders) └─ order_year=2025/ ├─ order_month=1/ part.parquet ├─ … ├─ order_month=6/ part.parquet ◀ the only file opened └─ order_month=12/ part.parquet

WHERE order_year=2025 AND order_month=6 → 1 file read.
No filter → 24 files read. The cheapest query is the one that never touches the data.

✓ order_year / order_month
24 folders · matches the filter · similar sizes
✕ customer_id
200,000 folders of ~25 rows → the small-files problem: listing and opening files costs more than reading data
⚠ country
IN holds 17% of rows, BR only 5% → skew: one partition 3× its peers, one worker still busy while the rest idle
ParquetORCAvro
Layoutcolumnarcolumnarrow
Best foranalytics, lakesHive / Hadoopstreaming, Kafka
19:30 (1.5 min). Folder names ARE the partition values, so the engine prunes by path without opening anything. Rule of thumb: low-cardinality columns you always filter by (date, region); never ids. Skew (country) is the Session-2 exercise. Formats: Parquet is the default for analytics; ORC is its Hadoop cousin; Avro is row-based, used when streaming records.

5 · Live demo · the race
22:00 (5 min). Go through the tabs in order, ask the room to predict the winner first, then Run all four. 1 Point lookup: Redis and Postgres sub-ms; DuckDB/S3 are OK only because ids are sorted (min/max skipping). 2 One customer's orders: Postgres index wins; columnar must scan. S3 writes a brand-new object per row (small-files problem). 6 Change one value: S3 rewrites ~205k rows to change one. Parquet is immutable, hence Iceberg/Delta (Session 4). Wrap-up

Three things to remember

  • ① Layout is architecture. Row vs column, sort order and partitioning decide speed and cost, before any tuning.
  • ② One store never fits all. Hot → RAM, transactional → row store, analytical → columnar, everything else → cheap object storage.
  • ③ The cheapest query touches the least data. Skip with stats, prune with partitions, project only the columns you need.
